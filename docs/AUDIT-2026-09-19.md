## Iframe coverage

The server covers all three distinct iframe surfaces:

1. Settings iframe: application create/update exposes `registration_redirect_url` and `is_iframe`.
2. Entity frames: `integrations_hub_list_entity_frames` and `integrations_hub_replace_entity_frames` manage complete `employee`, `client`, and `visit` declaration sets.
3. Internal sidebar frames: `integrations_hub_install_sidebar_frame` and `integrations_hub_toggle_sidebar_highlight` manage `chat`, `waiting_list`, and `task_tracker`. Activation also accepts `chat_url`.

The contracts correctly preserve the important platform limits: declarations are full replacement, existing installations are not backfilled, entity-frame `postMessage` is origin-bound, and the partner API cannot read back effective per-location frames. A successful sidebar write is therefore reported as unverified rather than as proven materialization.

This audit adds explicit iframe input descriptions and output schemas for all four dedicated frame tools, marks sidebar frame mutation as potentially destructive, and requires `REMOVE ...` rather than `INSTALL ...` when `url: null` deletes a sidebar frame.

## Contract quality

Strengths:

- strict Zod objects reject unknown fields;
- IDs, enums, URL formats, date formats, bounds, and full-replacement hazards are validated;
- public vocabulary uses `location`, translating legacy wire-level `salon` fields internally;
- every mutation has `plan | apply`; sensitive writes require exact confirmations;
- partner actions verify caller ownership and fetch the owned account token server-side;
- credentials are recursively redacted.

Remaining weaknesses:

- only the four dedicated iframe tools declare MCP `outputSchema`; the other 29 return raw or lightly wrapped upstream objects;
- some historical upstream names remain inside nested application payloads (`is_multiple_salons_allowed`), because Biz.ERP accepts only those wire names;
- response normalization is inconsistent between read tools (raw upstream envelopes) and mutations (`ok/applied/operation/data` wrappers);
- upstream Developer Cabinet routes are implementation APIs, not stable public contracts;
- Marketplace backoffice routes are not exposed by this public MCP.

Input descriptions improved from 23/154 (15%) to 112/154 (73%) top-level properties in this audit. The remaining undescribed fields are mostly tool-specific operational fields and should be completed together with output normalization.

## Test quality

`npm run check` passes lint, formatting, TypeScript, Jest, and build. CI additionally builds the Docker image and health-checks the container.

After this audit there are 26 tests across client auth, safety, redaction, HTTP initialization, idempotency, lifecycle signatures, and iframe behavior. Coverage is still modest: 56.0% lines overall and 41.5% in `tools.ts`; there is no enforced coverage threshold and no live Biz.ERP contract test in CI. The iframe paths are better protected than the overall tool set, including schema publication, duplicate-slug rejection, replacement read-back, sidebar install reporting, and explicit remove confirmation.

Recommended next step: add a non-mutating contract suite against an approved Biz.ERP environment and normalize/output-schema the remaining tool families before treating the MCP interface as a stable versioned API.
